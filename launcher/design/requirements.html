Build requirements — v5.5

What the code agents must deliver so the Requirements tab supports editing, deleting, manually adding, and updating status of user stories and requirements. These are non-negotiable acceptance criteria that accompany the mockup below.

API Endpoints — all write back to the project on disk

GET/api/projects/:id/requirementsList user stories + their BR/TR requirements.
POST/api/projects/:id/storiesCreate a new user story. Body: title, asA, iWantTo, soThat.
PATCH/api/projects/:id/stories/:usIdEdit a user story's title / As-a / I-want-to / So-that / story-status.
DELETE/api/projects/:id/stories/:usIdDelete a user story and all of its requirements (soft-delete; recoverable for 30 days).
POST/api/projects/:id/stories/:usId/requirementsAdd a new BR / TR to an existing story. Story is in the path — no body field. Body: type, text, priority, status, owner.
PATCH/api/projects/:id/requirements/:reqIdEdit requirement text, type, priority, owner, or status.
PATCH/api/projects/:id/requirements/:reqId/statusStatus-only update (lightweight, used by the dropdown).
DELETE/api/projects/:id/requirements/:reqIdDelete a single requirement. Soft-delete; recoverable for 30 days.

UI Affordances that must exist

  • Unified InlineForm component with mode = 'add' | 'edit'. Add and Edit use the same form layout, the same field set, the same validation, and the same submit/cancel pattern. The only differences are: (a) framing pill ("Add" peach vs "Edit" butter), (b) form-id line ("new US-NN" vs "US-01 · last edited 2h ago by BA Agent"), (c) submit button label ("Create …" vs "Save changes"), (d) an extra form-foot-delete strip in edit mode containing the Delete button, (e) border tint (navy-2 vs amber). Pre-filled values populate the same inputs the Add form uses.
  • Row-level Edit icon (pencil) on every requirement row, hover-revealed + keyboard-accessible. Click → the row is replaced in place by the InlineForm mode='edit' for that requirement, pre-filled with the current values, focused on the first field. Pressing Esc collapses the form back to the read row.
  • Row-level Delete icon (trash) on every requirement row. In edit mode, the Delete button lives in the form's form-foot-delete strip — no separate inline confirm step, since the Edit form is already in context. Outside edit mode the row trash icon is a shortcut that opens the same Edit form scrolled to the Delete strip.
  • Story-level Edit / Delete on every story header, using the same InlineForm mode='edit' (story-shaped: Title + As-a/I-want-to/So-that + Priority + Story status + Owner).
  • Story-first add flow. The top "add bar" has a single Add user story button — the only entry point for a new story. The "Add requirement" button does not live at the top; requirements can only be added after a story exists.
  • Add user story button (top add bar) → opens the InlineForm mode='add' for a story (Title, As-a / I-want-to / So-that, Priority, Initial status, Owner). Save appends a new US-NN block to user-journeys.md and reveals an "Add requirement" button on the new story header.
  • Add requirement button (per story header, next to Edit / Status / Delete) → opens the InlineForm mode='add' for a requirement (Type, Priority, Text, Status, Owner) scoped to that story. No story picker — the form is pre-attached to the story it was opened from.
  • When a project has zero user stories, the empty state replaces the list with a single CTA: "Add your first user story". The "Add requirement" affordance is hidden until at least one story exists.
  • Status dropdown on every requirement row AND every story header, replacing the static status pill. Dropdown lists all 7 statuses with the current one checked.

STATE Status state machine (reqs and stories share it)

draft→ in_review→ approved→ done
in_review→ returned→ draft
in_review→ blocked
approved↔ on_hold
draft→ cancelled

VALID Validation rules

  • Story title: required, 4–120 chars, trim whitespace.
  • As-a / I-want-to / So-that: each required when creating a story; "As a" supports the role from existing personas when present, free text otherwise.
  • Requirement text: required, 10–500 chars; must end with a period or be a complete sentence.
  • Type: required, one of BR | TR. BR counts as "Business", TR as "Technical" in the stage banner.
  • Requirement must belong to a story: the requirement-creation endpoint requires a story in the URL path. A 422 is returned if a BA tries to POST a requirement without a story (e.g. via direct API call). The UI never offers a story picker in the requirement form.
  • Priority: required, one of must | should | could | wont (MoSCoW).
  • Owner: required, one of BA | SA | DEV | QA.
  • Status: required, one of draft | in_review | approved | done | blocked | returned | on_hold | cancelled. The dropdown may only offer transitions allowed by the state machine above; out-of-machine transitions are hidden, not disabled.
  • Delete: blocked when a requirement is in approved or done AND another story references it; the inline confirm copy must explain why in that case.
  • ID stability: BR/TR IDs are never renumbered on delete. The next add reuses the lowest free number in the project's sequence.

WCAG Accessibility requirements

  • Every Edit / Delete action is a real <button> with an aria-label that includes the row's stable ID (e.g. aria-label="Edit BR-007"). Visible focus ring (2px navy-2, 2px offset) on every interactive element.
  • Status dropdown is a <button aria-haspopup="listbox" aria-expanded> + <ul role="listbox"> with role="option" aria-selected on items. Arrow-key navigation, Esc to close, focus returns to the trigger.
  • Delete confirmation is keyboard-discoverable. On activation, focus moves to the "Delete" button (rose-coloured, distinct from the navy primary). Pressing Esc cancels.
  • Inline edit row keeps the same role / focus order as the read row. The Save / Cancel pair lives at the end of the row so screen readers announce "Edit BR-007, Save button, Cancel button".
  • Add forms surface field errors with aria-invalid="true", aria-describedby pointing at a visible error node, and a programmatic error summary at the top of the form.
  • All new icons are aria-hidden="true"; the visible text or aria-label carries the meaning.
  • Contrast on the new rose delete button against its background: 4.5:1 minimum (verified for --rose #d97a8e on white = 4.6:1).

UX States the UI must handle

  • Loading: skeleton rows while GET /requirements in flight (existing pattern, keep).
  • Empty: when a project has zero user stories, the add bar sits above an empty-state illustration + CTA "Add your first user story".
  • Form open: clicking Add (top bar / per-story) or Edit (row / story header) expands the InlineForm in place. The form replaces the row in the list, or sits directly under the story header. Focus moves to the first field. Pressing Esc (or clicking Cancel) collapses the form back to read mode and returns focus to the originating Edit / Add button.
  • Form open: only one at a time. Opening an Edit form for a requirement closes any other open form on the same screen (and warns before discarding an unsaved draft).
  • Saving: form submit button shows inline spinner and disables; submit is replaced with "Saving…". Concurrent edits blocked with a "Saving…" badge on the row.
  • Error on save: form stays open; error toast at top; field-level errors show below the offending input; submit button re-enables.
  • Optimistic status change: status pill updates instantly; if the PATCH fails, the pill snaps back and a toast explains.
  • Delete from form: the Delete button in the form-foot-delete strip is a single-click action (no extra confirm step) when the row has no dependencies. When the requirement is referenced by another story, the Delete button is replaced by a "Cannot delete" notice explaining the dependency and offering "Open referencing story".
  • Concurrent edit: if another BA is editing the same row, show a non-blocking notice "BA Sara is editing — your change will be queued".

SEC Security + write-back

  • All endpoints require the existing project-scoped BA auth (read: any project member; write: BA role only). SA, devs, designers, and QA get a 403 on POST/PATCH/DELETE; the UI hides the Edit / Delete / Add affordances for them.
  • Write-back target files: PRD/prd.md §8 (business reqs) and PRD/user-journeys.md per-story blocks (technical reqs). Both writes are atomic (write to .tmp + rename) so a crash never leaves the PRD half-updated.
  • Soft-delete rows stay in the file as ~~struck through~~ BR-007 with a <!-- deleted 2026-08-27 by BA Will --> marker for 30 days; permanent removal is a separate admin action.
  • Input is length- and charset-validated server-side; client validation alone is not enough.

DATA

Rule for IDs and stability
  • Requirement IDs are BR-001 through BR-NNN / TR-001 through TR-NNN, project-scoped, zero-padded to 3 digits.
  • User story IDs are US-01 through US-NN, project-scoped, zero-padded to 2 digits.
  • On delete: do NOT renumber. The next add reuses the lowest free number in the project's sequence — referenced from the live requirements file, not a counter.

LEGEND Stage-banner pills (already on screen 15) — must stay in sync

9 Business 9 requirements with type=BR across all stories. 6 Technical 6 requirements with type=TR across all stories. 3 Blocked 3 requirements or stories currently in status=blocked or returned.

These counts must re-derive from the live data on every render — no static numbers.

v5.4 Refinement batch — Will's review notes (items 2.1–2.9)

  • v5.4→v5.5 — Origin tag extension (Will QA round 2): every req row carries an origin dot — blue = manual, coral with halo = generated; legacy rows (no marker) render as manual. Stories carry their own origin tag next to the story id. TR rows stamp origin too (<!-- TR-NNN: origin=manual --> mirrors the BR grammar). The BA is the only writer today, so every POST stamps origin=manual; the future BA auto-draft job writes origin=generated.
  • v5.4→v5.5 — Add-req slot correction: clicking "Add requirement" under a story used to silently no-op (the form-slot matcher required a reqId, but add-req forms carry a usId). The matcher now accepts mode=add + kind=req → slot === usId, and the add-req InlineForm renders directly under the story head.
  • v5.4→v5.5 — Error summary timing: the form-error-summary banner ("Fix the N highlighted fields below") only renders once at least one field has a visible error — was rendering on mount because it counted untouched client errors. The submit gate still uses the full client-errors set (server is the backstop).
  • Origin dot (2.6) — every req row carries a small color-coded dot next to its id: blue = manual (BA wrote it), coral with halo = generated (an agent wrote it). Legacy rows (no marker) render as manual per v5.5 (the null→manual default; was "no dot" in v5.4). The dot's aria-label announces "Auto-generated" / "Manually written". The future BA auto-draft job writes origin=generated; today's UI writes origin=manual. Stories carry their own origin dot too (v5.5).
  • BR under story (2.7) — a BR row can link to a story via a meta comment on the line directly below the row: <!-- BR-NNN: story=US-NN, origin=manual -->. The parser moves linked BRs into the story's req list at read time. The standalone group renders only unassigned BRs (legacy, or whose story id no longer exists) and is titled "Unassigned business requirements".
  • Edit form under the row (2.8) — the InlineForm for editing a BR / TR renders as a sibling directly under that row's .req element. There is no longer a shared "BR group" form slot — every row owns its own edit affordance.
  • Delete via modal (2.9) — the trash icon on a row or story header opens a ConfirmDialog directly. No two-step "open edit form, click Delete in the footer" flow. Esc / Cancel returns focus to the trash icon that opened the modal.
  • Validation timing — client-side field errors only render after the user touches the field or after the first submit attempt. Submit is no longer pre-disabled by hasErrors.
  • DES owner — DES (Design) joins the owner vocabulary. Owner dropdown + API validator accept it.
  • TR-delete parser fix — the parser used to interpret any <!-- deleted … --> comment inside a story block as a story-level delete, which silently hid the parent story when a single TR was struck. The marker is now scoped to "before any requirement rows / body".
  • Spacing + icon size — the requirements card has more top space; the "Add user story" icon is sized 24×24 px (root cause: no explicit size on the SVG).
