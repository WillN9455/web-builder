# Template selection rules (Build stage)

Starter project scaffolds that each Code Agent can use as a base for the generated application. Templates are chosen based on the user's stack preferences defined in [`../../build/config/config-rules.md`](../../build/config/config-rules.md).

## Available Templates

| Template | Framework | Best For | Stack |
|----------|-----------|---------|-------|
| `nextjs-starter/` | Next.js 14+ (App Router) | SSR, SEO-heavy sites, most web apps | React + TypeScript + Tailwind |
| `flutter-starter/` | Flutter 3.47 *(provisional pin)* | Native iOS/Android apps, mobile-first products | Dart + Material 3 |
| `vue-nuxt-starter/` | Nuxt 3 *(roadmap — not yet in the tree)* | Vue ecosystem teams, simpler apps | Vue 3 + TypeScript + Pinia |
| `sveltekit-starter/` | SvelteKit *(roadmap — not yet in the tree)* | Performance-critical, minimal JS | Svelte 4 + TypeScript |

The manifest's `templates` key promises `nextjs-starter/` and `flutter-starter/` — the roadmap rows are intentionally not in the contract until they exist.

## Template Structure

Every template is copied in as the project root, and every template follows the
same conventions (token wiring, file organization, test layout) — but the
directory shape differs between web and native.

### Web templates (`nextjs-starter/`)

```
project-root/
├── app/                 # Route-level pages (App Router)
├── src/
│   ├── components/      # Shared UI components (from design-system)
│   ├── hooks/           # Custom React hooks
│   ├── services/        # API service layer
│   ├── utils/           # Pure utility functions
│   ├── lib/             # Framework-specific utilities
│   └── styles/          # Global CSS, token imports
├── public/              # Static assets (favicons, SVGs)
├── tests/               # Unit + integration tests
├── .env.example         # Environment variable template
├── tailwind.config.js   # Design token configuration
└── tsconfig.json        # TypeScript configuration
```

### Native templates (`flutter-starter/`)

```
project-root/
├── lib/
│   ├── main.dart        # Entry point + screen landmarks
│   ├── theme/           # tokens.dart (compiled tokens) + app_theme.dart (ThemeData)
│   ├── features/        # Screens/widgets, feature-first (from design-system)
│   ├── services/        # API service layer
│   └── utils/           # Pure utility functions
├── test/                # Unit + widget tests (mirrors lib/)
├── android/ · ios/ · …  # Generated by `flutter create .` — not in the template
├── .env.example         # Build-time config template (--dart-define)
├── analysis_options.yaml # Lint + analyzer rules
└── pubspec.yaml         # Dependencies + bundled fonts (design tokens)
```

## Template Selection Rules

When choosing a template, reference `../../build/config/config-rules.md` for the decision tree.

- **Native app (iOS/Android) → `flutter-starter/`.** Choose this whenever the
  deliverable is a native mobile app — the PRD's §5 Target Users names
  app-store / device distribution, or the user's framework answer is a native
  stack. Do not scaffold a web app and wrap it: the native starter exists so
  this case is never silently defaulted to Next.js.
- **Web app → `nextjs-starter/`** (the default). Use it unless the user
  specifies otherwise or their requirements strongly favor another option
  (e.g. existing Vue team → `vue-nuxt-starter/`, once it exists).
- The `flutter-starter/` platform folders are generated: after copying, run
  `flutter create .` to bootstrap `android/` and `ios/` (see that template's
  README §Scaffold steps).

| config-rules section | Template file | What it fills in |
|------------------------|---------------|-----------------|
| Frontend Framework table → "React + Next.js" | [`../nextjs-starter/app/layout.tsx`](../nextjs-starter/app/layout.tsx) | SSR setup, App Router structure |
| Frontend Framework table → "Flutter (native app)" | [`../flutter-starter/lib/theme/app_theme.dart`](../flutter-starter/lib/theme/app_theme.dart) | Token → `ThemeData` mapping, Material 3 scaffold, platform-folder bootstrap |
| Database table → PostgreSQL/MongoDB | `../nextjs-starter/` DB config file | Connection string from PRD §3 Dependencies; user credentials from `.env.example` |
| Hosting Platform table → Vercel/Netlify | `../nextjs-starter/` deployment config | Edge region, build output, runtime config |

| API Communication table → REST/GraphQL | `../nextjs-starter/app/` route structure | Route pattern per coding-guidelines.md file organization |
| API Communication table → REST/GraphQL | `../flutter-starter/lib/services/` service layer | Client is public — endpoint from `--dart-define`, privileged calls behind a BFF |

## How Code Agents Use Templates

1. Confirm tech stack with user via `../../build/config/config-rules.md` questions — including whether the deliverable is a **web app** or a **native app**, which decides between `nextjs-starter/` and `flutter-starter/`
2. Copy the chosen template into a new branch. For `flutter-starter/`, bootstrap the generated platform folders with `flutter create .` (they are not in the template) — see that template's README §Scaffold steps
3. Replace all placeholder tokens (`{{PROJECT_NAME}}`, `{{PRIMARY_COLOR}}`, etc.) with project-specific values — **all color values must come from the project's `design-system/tokens/color.md`**, all typography from `typography.md`, all spacing from `spacing.md`
4. Implement features per PRD and design spec on top of the scaffold — each feature maps to a user story in PRD §8 + a component from the project's `design-system/components/README.md` index
5. Every skill file (coding-guidelines, security, accessibility, code-quality, feature-fidelity, ui-best-practices) must be applied during scaffold fill and feature implementation

## Template → Skill Mapping

Skill files live in `../../build/skills/` unless noted.

| File in template | Skill file that governs it | Specific rules |
|-----------------|---------------------------|---------------|
| `app/layout.tsx` | `coding-guidelines.md` (naming, components) + shared `security.md` §Headers & Configuration | Component organization; security headers |
| `globals.css` / token imports | project `design-system/tokens/README.md` + `color.md` + `typography.md` | All custom properties match token names and values |
| `lib/main.dart` *(Flutter)* | `coding-guidelines.md` (naming, widgets) + `feature-fidelity.md` §Read the Design First | Screen landmarks (`Semantics(header: true)`), AppBar → body order; no literal colours/sizes |
| `lib/theme/tokens.dart` + `lib/theme/app_theme.dart` *(Flutter)* | project `design-system/tokens/README.md` + `color.md` + `typography.md` | Tokens are the only place a colour/size literal may appear; `ColorScheme` built from token values, never `fromSeed` |
| `pubspec.yaml` *(Flutter)* | `coding-guidelines.md` + `../../build/config/config-rules.md` §Frontend Framework | SDK constraint matches the pinned Flutter version; `{{PRIMARY_FONT}}` declared in the `fonts:` block |
| `.env.example` *(Flutter)* | shared `security.md` §9 secrets management | Build-time values via `--dart-define` only; the client binary is public — no service credentials |
| `src/components/` files | `feature-fidelity.md` §Read the Design First; project `ui-best-practices.md` (all sections) | Each component traces to a design spec in the project's `design-system/components/`; all states from state docs implemented |
| `src/services/` files | shared `security.md` (all rules); `code-quality.md` (§search before creating, atomic DB ops, timezone rules) | Auth guards first; IDOR prevention; validation schemas; no predictable IDs |
| `tests/` files *(web)* / `test/` files *(Flutter)* | [`../../qa/skills/testing-guidelines.md`](../../qa/skills/testing-guidelines.md) §Test File Organization | Test naming per PRD user story (#N); every test traces to a requirement |
